# 운영 환경 진단 기록

Vercel(Hobby, 1 vCPU / 2GB)에서 검사를 돌리며 발견한 문제와 결정을 기록한다.
측정 환경: Vercel Fluid compute, playwright-core + @sparticuz/chromium.

## D-01. Mobile 검사가 멈춤
- 증상: Mobile 검사가 약 179초 동안 끝나지 않았다.
- 원인: @sparticuz/chromium은 `--single-process`로 실행되어 브라우저 하나에 컨텍스트를 하나만 열 수 있다. 한 브라우저에서 Desktop 다음 Mobile 컨텍스트를 열면 멈췄고, 타임아웃도 실제 실행을 끊지 못했다.
- 대응: 뷰포트마다 새 브라우저를 띄워 순차 실행한다. 모든 단계를 Promise.race 타임아웃으로 감싸고, 시간 초과 시 프로세스를 강제 종료한다.

## D-02. 실행을 반복하면 인스턴스가 느려짐
- 증상: 같은 인스턴스에서 8~9번 실행한 뒤부터 느려지거나 실패했다.
- 원인: 종료된 Chromium의 크래시 덤프가 /tmp에 쌓여 용량을 채웠다.
- 대응: 검사 시작 전과 종료 후 /tmp의 Chromium 임시 파일을 정리한다.
- 결과: 정리 후 연속 26회 실행이 모두 성공했다.

## D-03. Desktop 스크린샷이 느리고 자주 실패
- 측정: Desktop 스크린샷은 로컬에서 0.1~0.3초, production에서 12~60초가 걸렸다.
- 원인: 서버리스 환경에는 GPU가 없어 렌더링이 CPU(SwiftShader)로 처리된다. 특히 WebGL·애니메이션이 있는 페이지에서 크게 느려진다.
- 시도했지만 효과가 없던 것: CDP 설정, requestAnimationFrame 일시 정지, JS 실행 정지. 같은 페이지에서 재시도하면 같은 이유로 다시 실패했다.
- 대응: 스크린샷은 표시용이므로 실패해도 측정 결과는 남긴다(상태는 completed 유지, `SCREENSHOT_FAILED`는 스크린샷 실패만 뜻한다). 실패한 영역은 측정한 레이아웃 정보로 그린 배치도로 대체한다.

## D-04. 검사 브라우저의 WebGL을 끄지 않기로 결정
- 제안: GPU가 없어 느리니 검사용 브라우저에서 WebGL을 비활성화하자는 의견이 있었다.
- 결정: 채택하지 않았다.
- 이유: WebGL을 쓰는 사이트는 WebGL이 없으면 오류 화면이나 빈 화면을 띄운다. 그 화면을 검사하면 실제 사이트에는 문제가 있어도 "이슈 0건"이라는 잘못된 결과가 나온다. 느린 것보다 틀린 결과를 내는 것이 더 나쁘다고 판단했다.
- 기록: 이 결정은 코딩 에이전트가 근거와 함께 제안을 반박해서 내려졌다.

## D-05. 동시 검사 수 제한
- 결정: 배포본은 동시 검사 1건으로 제한하고, 초과 요청은 429로 안내한다.
- 이유: 1 vCPU에서 Chromium 두 개가 겹치면 둘 다 시간 초과될 가능성이 높다. 둘 다 실패하는 것보다 하나를 확실히 성공시키는 쪽을 택했다.
- 확장 계획: 검사 워커를 Docker로 분리하고 대기열에서 하나씩 꺼내 처리한다. 동시 처리 수는 서버 vCPU·메모리에 비례해 늘어난다(수치는 추정이며 측정 예정).
